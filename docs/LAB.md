## 2. Case schema (`cases.py`)

One JSONL row per case:

```
{id, kind, target, fields:[key…], site_state:<EditorState>, context:<turn context>,
 request:"<NL text>", expected:{ops:[…], diff:[{path,before,after}]},
 holdout:bool, manifest_hash, engine_fingerprint, template:"editorial",
 meta:{section_type, field_type, slot_values, generator, seed, measured:{warnings, written, engine_commit}}}
```

**Engine identity.** `expected.diff` is only as good as the engine that measured it, and the engine changes under the lab (cookie-cutter `ops/*.js` is edited by another workflow; on 2026-10-01 a reset/restore_default change moved 4 of 200 expected diffs after they were measured). So every measurement is stamped with `engine_fingerprint` = `engine.engine_fingerprint()`: sha256 over the name (relative to `launcher/client`) and content of every source in the **static import closure of `headless.mjs`** (`engine.import_closure`: relative and client-root `/src/…` specifiers of `import … from`, `export … from`, `import '…'` and `import('…')` walked recursively, resolving `.js/.jsx/.mjs/.ts/.tsx` and `index.*`; on 2026-10-01 that is the eight `ops/*.js` modules plus `src/data/pageSections.jsx`, `src/components/basicEditor/constants.jsx`, `src/utils/locationDetailSections.js`, `src/lib/cdnUrl.js`) united with every other `ops/*.js` / `*.mjs` source (`*.test.js` excluded — tests do not change what the engine writes), the `@breadstack/*` workspace packages met as `name@version` (their trees are not walked), plus `HEAD <commit>` of the cookie-cutter checkout when git can tell it (`meta.measured.engine_commit` keeps the commit readable; `ops/` itself is untracked there, so HEAD alone would see none of it). Before the closure the fingerprint covered `ops/*` only and an edit to `src/data/pageSections.jsx` — where `getDefaultPageSections`/`getAvailableSectionsForPage`/`BASIC_TEMPLATE_IDS` live — left it unchanged (refuter, 2026-10-01); `tests/test_engine.py` now edits a scratch copy of that file and asserts the fingerprint moves. The fingerprint is part of the engine's disk/memory **cache key** (`engine.request_hash(…, engine_fingerprint)`), so a diff cached under another engine is never reused; it is stamped on cases, collector rows (`meta.engine_fingerprint`), HF rows (`meta.engine_fingerprint`, the case's), `dataset-manifest.json` (`engine_fingerprint` of the build's engine, `case_engine_fingerprints` seen), eval runs (`engine_fingerprint`, `stale_cases`) and verify results (`engine_fingerprint`, `case_engine_fingerprint`, `engine_mismatch`). `verify` and `dataset` warn when a case was measured with another engine; `eval` lists the stale exam cases; `souschef-lab cases remeasure --cases X` (`make cases-remeasure CASES=…`) re-runs every expected op through the current engine and rewrites X in place, reporting `changed`/`unchanged`/`stale_before` and the ids whose diff moved; `make engine-fingerprint` prints the identity. A case whose ops the new engine refuses is dropped to `X-rejects.jsonl` (exit 2), as `cases` does at generation.

*Fingerprint move of 2026-10-03 (`9e912a0c…` → `bc880927…`, cookie-cutter master `388825c1` + the uncommitted `headless.mjs` edit).* `headless.mjs` now loads `src/sousChef/host/previewApi.js` through the same Vite runner and passes the ops through the host's `withTargetDefaults(ops, ctx)` before `applyOps`, exactly as the browser host does: a `section`/`page` target (or a `set_page_layout`/`reset_pinned_section` op) that omits `page` takes `ctx.currentPage`, and a `location-details` target without `storeId` takes `ctx.editingStoreId`. The headless parity is tested in cookie-cutter `ops/headless.test.js` (3 cases, real child-process boots) and here in `tests/test_engine.py::test_bare_section_target_is_filled_from_ctx_current_page`. The same day `verify.ctx_of` started sending `currentPage` too (it built `templateId` + golden ctx + `locations` only, while `collect.ctx_for` sent `currentPage` live): without it the replay would have refused the very op the collector's engine now accepts, and a correct bare-target turn would have read `invalid_op` from run 3 on (`tests/test_verify.py::test_ctx_of_carries_the_viewed_page_like_the_collector`). **Run-2 rows are not rescued by the fix** (expected, measured): verify-2 replays *every* `tool.call` of a trace, so an error+retry pair whose first op now applies is applied twice. - `kind` ∈ `set_field | set_enum | set_range | toggle | image | list_add | list_remove | list_reorder | list_update | reset | layout | multi | clarify | unsupported`.
- `target` is the engine union (FACTS 2 §1): `{kind:'section',page,sectionId}`, `{kind:'global',panel}`, `{kind:'branding'}`, `{kind:'page',page}`.
- `site_state`: the `golden.test.js:104` empty shape with `template:{id}` one of the ten basic templates (never `default`: section adds fail E_TARGET — FACTS 2 §1) and `homeSections` = `DEFAULT_DEFAULT_HOME_SECTIONS` rows (heroBanner, featuredCategories, productCarousel-1/2, testimonials, contentBlock-1/2/3, gallery, contentBlock-features/icons, blogSection, newsletter), rich settings seeded from `probe-sample.json` variants.
- `context` = `state.context_of(state, page)`: `page`, `template`, `layout` (`layouts[page] or 'default'`), `sections=[{id,type,title,enabled}]` (type = id minus `-\d+`), `categories/customPages/nav/locations` from fixtures (`ref` fields take their slugs from here). Since 2026-10-10 also `focus` (default editor, nothing open), `shopMenu` and the manifest-derived list `outline` (`context_of(state, page, extras, manifest)`; cases pass the manifest, as the browser always has it loaded); `tests/test_state.py::test_context_of_matches_the_browser_golden` asserts the browser's own output in cookie-cutter `launcher/client/src/sousChef/__fixtures__/turnContext.parity.json`.
- `expected.ops`: `{op, target, …}` as the model should emit them (`tool.call.name` = op, `input` = the rest; README §1.2). `expected.diff` is **measured**: `engine.run(site_state, expected.ops, ctx)` → `changes[].diff` leaves. Expected ops that fail in the engine are a generator bug; the case goes to `cases-rejects.jsonl`.
- `holdout`: `sha1(field_key) % 100 < 20`, `field_key` = `<container>.<field or list path>`; independent of wording, so paraphrases never straddle train/exam (thermometer's question-hash idea, FACTS 1 §1).
- `manifest_hash`: README §1.1 recipe, tested against the vector `727d151b…`.
- `request`: per-kind templates (≥ 4 each) with slots `{section_name} {field_label} {value_phrase}` and verb/politeness variants, seeded by case id. **Unambiguous by construction** (int-run1 finding B, 2026-10-04 — 195 of 1,200 rows were `no_answer`, most of them the model asking a *sensible* clarifying question: "Clear the color on the checkout page" for `sectionStyle.color` when checkout has four `Color` fields, "body text color → …" for `productDetail.reviewTextColor` whose label is `Body Text Color` while 'body text' names the `Body Text` pair, "Remove the text from the product-details page" for one of seven `Text` chips, "The third content block — address → …" for `locationOverrides.loc-main.address` with three locations in context, and two sections both titled 'Why Choose Us?' named by title):
  - **Field = its manifest label**, verbatim, the text `lookup_fields` returns — group segments kept (`Tagline › Text size in pixels`), parentheticals kept (`Background Image (Mobile)`) except the `(optional)` residue (`Tagline Image (optional)` → `Tagline Image`; the residue-only `Or pick from locations` falls back to the key's words, as an empty label does); a `{item}` placeholder takes the **item's display name** (`cases.item_display`, refuter B D2 2026-10-04): the keyed segment of a keyed key (`pageVisibility.our-story.inHeaderNav` + `Show {item} in header nav` → `Show Our Story in header nav`, a fixture custom page / location by its title), a list row's item noun (`promotion.items[].enabled` + `Hide {item}` → `Hide tier`), or for a flat key the key's words the label does not already say with abbreviations expanded (`btnColor` + `{item} Color` → `Button Color`, `overlayColor` + `Overlay {item}` → `Overlay color`) — never the leaf's words when the leaf is not the item (`Show in header nav in header nav`, `btn color` were the bug). The snapshot's `inFooterNav` labels carry the probe's own name (`Hide Probe text 2 from footer`); `Probe text N` is read as `{item}` (`cases.label_text`).
  - **Toggles are phrased by effect** (refuter B D1, 2026-10-04 — 10 of 3,078 cases read "Turn off Hide Shop from header nav for the header." with expected `{inHeaderNav: false}`): a nav toggle's manifest label is the state-dependent aria-label snapshotted in the visible state (`HeaderNavigationEditor.jsx:164`: `Hide X from header nav` when visible, `Show X in header nav` otherwise) while the engine's value is true = visible (`:222-229`), so "turn off Hide Shop" meant SHOW = true and the case expected false. A bool whose label starts with a visibility verb (`cases.NEGATED_LABEL`: Hide / Show / Don't / Disable / Remove / Exclude / Skip) is never asked for as "turn on/off <label>"; the request is the imperative that produces the expected value (`cases.toggle_effect`, templates `EFFECT_TOGGLE_TEMPLATES`): value false → `Hide Shop from the header nav`, value true → `Show Shop in the header nav`; `Hide THC pill` (`cardShowTHC`) + false → `Hide the THC pill`. The value's meaning comes from the **key's polarity** (`cases.key_is_negative`: a `hide`/`hidden`/`disable`/`off` word in the key or its first segment → true = hidden; otherwise true = shown), so `hideImageEmptyBg` + true → `Hide the empty image background`. Negated labels on the snapshot: `HeaderSection pageVisibility.<page>.inHeaderNav` (10 `Hide … from header nav` + `our-story` `Show {item} in header nav`), `FooterSection pageVisibility.<page>.inFooterNav` (11, probe residue), `pageVisibility.<legal page>.inFooterBottom` (3 `Hide … from footer`), `footerLocationEnabled.{locationId}` (`Locations › Hide {item}`, never generated — unresolvable keyed), `ProductCardSection cardShow{THC,CBD,Category,Terpenes,PlantType,Tags}` and `product-details productDetail.show{Weight,THC,CBD,Category,Terpenes,PlantType,Tags}` (`Hide … pill`, positive keys), the hide-keyed `contentBlock/perksCards/perksIcons.hideImageEmptyBg`, `newsletter.hidePaddingTop`, `ShopMenuSection.shopMenuHideBorderTop`, `branding.locationPickerHideCardBg`, `faq.hideHeader/hideStillQuestions/hideMarkers`, `productDetail.hideFulfillment/hideCheckNearbyStores`, plus every `Show …` label (`showCategoryDescription`, `footerShowAppStore`, `paymentMethods.<m>` …). `meta.field_phrase` is the phrase the request carries (the effect imperative for these), `meta.label_phrase` the ambiguity guard's name, `meta.effect_phrased` the flag. Multi parts follow the same rule (`hide the padding top in the newsletter section`). `LayoutSection pageHeaderHiddenPages.<page>` (label `{item}` alone, negative parent key) is still a turn-on/off of `Our Story (pageHeaderHiddenPages)` — true = hidden, consistent but opaque.
  - **Ambiguity guard** (`cases.name_fields` over `cases.scope_fields` = the container's fields + the hero's mirror item fields + a page's `_common` fields; a list's row fields for `list_update`/`list_add`): when another field of the same target could be called by the same text, the phrase is qualified — label + type word (`Headline text` / `Headline color`), then label + dotted parent for nested keys (`Color (sectionStyle)`, `Heading (emptyState.headingStyle)`), then both (`Heading text (orders.heading)`); a **bool** sharing its label with a non-bool sibling is qualified by its key words instead of a type word (refuter B D3: `titleUppercase` 'Headline Font' beside the font select → `Headline Font — uppercase (titleUppercase)`; the legal pages' `headingUppercase`, mislabelled 'Headline Color' → `Headline Color — uppercase (headingUppercase)`; never `Headline Font toggle`); a candidate counts as unique only when no *other* field's candidate at any level equals it (case-insensitive). A field no candidate makes unique is **skipped** — `skip:ambiguous-label`, `Generator.skipped_ambiguous` lists `<container>.<key>` — never asked for ambiguously: on the snapshot 93 fields (148 before the generic-label rule below; e.g. `contentBlock.textAlign/splitContentAlign/contentTextAlign` = three `Text Alignment` enums, `HeaderSection.headerTextColor/headerMobileMenuTextColor` = two flat `Text Color` colours, `order-confirmation.orderConfirmation.*Btn*`). `multi` and `clarify` draw only from unambiguous fields.
  - **A generic one-word label is never handed out bare** (int-run2 finding B, 2026-10-03 — Sonnet, 300 × 4, pass@1 91.8%: "Reset the Text of the header" meant `HeaderSection.headerMegaMenuTextColor`, label `Text` under the editor's Mega menu group and the only `Text` in the header, so the guard passed it bare — and the model, like any reader, reset `headerTextColor` ('Text Color'); same shape for "Change the Background on the header" → `headerMegaMenuBg` read as `headerBgColor`, and "Layout should be Grid View" on the blog page → `layout` read as `set_page_layout`). A label whose single word is in `cases.GENERIC_LABELS` (Text, Color, Image, Background, Font, Size, Title, Headline, Heading, Body, Link, Icon, Border, Radius, Padding, Spacing, Width, Height, Alignment, Style, Hover, Placement, Layout, Name, Label, Tagline, Description, Message, Footnote, Logo, Arrow, Shape, Position, Divider, Columns, Placeholder, URL, Answer, Overlay, Opacity, Shadow, Gap, Mode) names a *property*, not a thing, so being unique in the manifest is not being unique in a reader's head: `cases.phrase_candidates` emits no bare candidate for it, **even when it is unique in scope**. It is located by its group label when the label has one (`Pill Hover Colors › Text` — `label_text` keeps the group, so these were never bare), else by the dotted parent (`Color (sectionStyle)`, `Message (announcementBar)`), else — a flat key, which the manifest carries without its editor group — by the key's other words, the nearest thing to the group heading (`cases.pseudo_group`: abbreviations expanded, the label's words, the type word and shared stems like `align`/`alignment` dropped: `Text (header mega menu)`, `Background (header mega menu)`, `Alignment (shop menu location)`, `Text (card thc chip)`), and when the label already says every key word by the key itself (`Headline (headline)`, `Layout (layout)`, `Footnote (footnote)`); the type word still breaks sibling ties (`Headline text (title)` / `Headline color (title)`). A generic **bool** keeps only its D3 key-qualified form. A phrase's **content words** (`cases.phrase_content_words`: qualifier tails stripped, then `CONTENT_STOPWORDS`, `GENERIC_LABELS` and type words dropped) collide with another container when **all** of them are in its vocabulary **and** at least one is a *distinctive* name word of it — a word in the vocabulary of at most `NAME_WORD_MAX_SHARE` (1/8) of the containers: `shop`, `brand`, `footer`, `cart`, `header` qualify; `button` (26 of 49 containers), `card` (19), `layout` (30), `content` (18) name nothing. On a collision `Generator._field_name` appends the field's own container's short name (`cases.short_container_name`: `branding`, `header` / `shop menu` / `branding settings` from `PANEL_LABELS`, `content block`, `blog page`): `Shop button placement (branding)`, `Shop button Border Color (branding)`, `Footer Logo (branding settings)`, `Show Cart Icon (header)`, `Brand Color (typography and colours)`, `Page Header Alignment (site layout)`. The tail survives effect phrasing (`Show Cart Icon (header)` → `Hide the Cart Icon (header)`). 52 of 1,784 phrases on the snapshot (2.9%; `test_b_phrases_naming_another_container_are_pinned_to_their_own` bounds it at 5%), a few of them spurious but true (`Service Options Title (content block)` via `service` ∈ terms-of-service). Not applied to list-row fields (a row is addressed by its list and index) nor to keyed phrases (they carry the location's name and id).
  - **Section = type label, plus the id whenever the type repeats on the page** (`the third content block (contentBlock-3)`, `the content block contentBlock-features`); a title names a section only when no other section on the page has it. **Page = the exact page id** (`the product-details page`), never a paraphrase. **Keyed fields name the concrete key by name and id** (`address override for the location 'Main Street' (loc-main)`). **Nested lists name the parent row** (`the third link of the first footer column of the footer`).
  - **Reset says `reset`/`clear` + the label** (never "remove"/"unset"); **restore says `default` + the label**.
  - `clarify` stays the one deliberately ambiguous kind — about the *section* (the type is named, several rows exist), never about the field.

### Generation rules (FACTS 2 §2 target enumeration)

| field type | op / value |
|---|---|
| text, richtext | `set_fields` with a slot-generated string; richtext wraps in `<p>` |
| bool | `toggle`: value = `not current` (current seeded in `site_state` so the diff is non-empty); a negated / visibility label is requested by effect (`Show Shop in the header nav` ↔ `inHeaderNav: true`), see above |
| enum, select | `set_enum`: a value from `enum` ≠ current; request uses the enum label when present |
| range, number | `set_range`: `min + k*step` within `[min,max]`, ≠ current; no min/max → integers 1–100 |
| color | `set_field` with `#rrggbb` |
| image | `image`: `set_fields` with `values[key]=asset.public_url` **and** `assets[key]={alt,srcset}` from `fixtures/assets.json` — on the hero's mirrored `backgroundImage` too (never `edit_list update` without `assets`: that measured alt `''` / srcset `null` while the model, correctly, wrote the asset's — warm-up #2, 2026-10-04); companions from `companions` (`…Alt`, `…SrcSet.<w>`) appear in the expected diff. The `url` variant's request names the asset **by its alt** (`the image 'Sunlit field at harvest'`; by its URL only when the alt is empty) and carries it as `meta.asset_id` — the model owns no asset library, so for an alt it opens the picker, and the collector's picker answers with **that** asset (`state.fixture_asset_for(assets, case_id, type, meta.asset_id)`; int-run3, 2026-10-04: while it answered the hash pick, 15 of the run's 21 `url` rows failed — 11 wrote the picker's asset (`wrong_value`), 4 refused it and asked (`no_answer`); the 2 URL-phrased and 4 lucky-hash rows passed). A second variant goes through `pick_asset` (expected ops: `pick_asset` then `set_fields` of **exactly the asset the collector's fake picker answers with** — `state.fixture_asset_for(assets, case_id)`, `sha1(case id) % len(pool)`, also stored as `meta.asset_id`, shared by the generator and `collect.pick_asset_for`; a pick whose asset equals the current value is skipped, `skip:pick-same-as-current`) |
| ref | value = a slug/id from `context.categories|tags|brands|locations` |
| keyed_by | key substituted with a real id: `locationOverrides.<locId>.<f>`, `categories.<slug>.<f>`, `footerLocationOverrides.<locId>.<f>` |
| derived_from | excluded from enumeration (28 fields, FACTS 2 §2); they appear only as `unsupported` asks |

- **Hero mirror**: the 56 mirror keys target `slides[0]` (FACTS 2 §2); expected ops use `edit_list update` on `slides` index 0 (README §3) — except images, which are `set_fields` + `assets` (above). The verifier compares leaves, never op shapes: the engine writes `slides[0].<k>` and the flat `<k>` for either form (measured 2026-10-01 for `headline`: `recorded.json` `H1_hero_flat` ≡ `H2_hero_list`; 2026-10-04 for `backgroundImage` with companions: `recorded-images.json` `F1_hero_image_set_fields` ≡ `L_hero_image_edit_list_with_assets`), and §3's two-way collapse makes them one write.
- **conditional_on / hidden_when**: the gate is set in `site_state` so the field is live (629 gated fields); a small variant set keeps the gate closed and expects `W_HIDDEN` (meta only).
- **unset**: `reset` where `unset_value` exists (963), `restore_default` where `default` exists (221); expected leaf = that value.
- **Lists** (69): actions from `ops` (`update` always allowed); nested lists use `index:[i,j]`; `orders` lists reorder by id array; page `sections` get add/remove/reorder/duplicate/update{enabled}. Item fields = `item` ∪ `details[item_ref].fields` minus `item.`.
- **layout**: `set_page_layout` over allowed layouts; `reset_pinned_section` once per page with a pinned id.
- **multi**: 2–3 independent ops on one page, requests joined with "and".
- **clarify**: two same-type sections on the page (`contentBlock-1/2/3`, `productCarousel-1/2`) and a request naming only the type. Expected: no ops, reply has "?" and ≥ 2 candidates.
- **unsupported**: premium/out-of-manifest asks (custom code, section types beyond the 19, A/B tests, third-party scripts, a `derived_from` field by name). Expected: `report_unsupported`, no browser ops.

Volumes are measured at generation, not promised: one positive case per writable field per home section, global panel and page (≈1,900 minus derived), ≥ 1 per list op, ≈ 60 clarify, ≈ 40 unsupported.

## 3. Verifier (`verify.py`)

Input: a trace (collector row or Postgres `traces.events`) and its case.

1. `tool.call` events in `seq` order minus `report_unsupported`, `pick_asset` and server tools (`lookup_fields`, `describe_target`) are the ops (`name` → `op`, `input` → fields).
2. Replay through `engine.run(case.site_state, ops, ctx)`, fresh state, golden ctx (`cdnUrl='https://cdn.int.breadstack.io', galleryFolder='gal', now=1700000000000`, FACTS 2 §1).
3. Normalise: indexes kept (list cases need them); a removed leaf compares as `after=None`; then, on the pair (rule version `verify-2`, 2026-10-04):
   - **Hero mirror, both directions** (`align_mirror`): a section is a mirrored hero when either side wrote under its `settings.slides[0]`; a flat `settings.<k…>` whose first key either side saw under `slides[0]` *is* the `slides[0].<k…>` write and moves onto the slide path (unless the slide path is present with another value — a real disagreement keeps both). Nested companions (`backgroundImageSrcSet.800`) collapse too; `verify-1` matched a bare key beside its own equal twin only, so the flat `SrcSet.<w>` leaves of a correct hero image write surfaced as `extra_writes`.
   - **Companion tolerance** (`set_aside_companions`): every `<k>Alt` / `<k>SrcSet` / `<k>SrcSet.<w>` (and parallel `<k>Alt[i]`) leaf whose image primary `<k>` **both** sides wrote is set aside, listed in the verdict's `companions`, and noted `companions` in `info` — present, absent or different alt/srcset never fail a matching URL (the case's asset metadata and the model's may legitimately differ), and a *different* URL is `wrong_value` on the primary rather than missing/extra srcset widths. A companion whose primary is on one side only is compared as any leaf.
   - **`pick_asset` substitution** (`substitute_picked`): a case with a `pick_asset` op is compared against the asset the picker actually returned (the trace's `tool.result` `asset`, else the row's `picked_assets`); when its URL differs from the asset the case was generated with, the expected browser ops are rewritten with it (`values[key]` / `item[key]` + `assets[key]`) and **re-measured through the engine** — exact by construction, no diff rewriting — `info: pick_substituted`; a refused re-measure keeps the case's diff and says `pick_remeasure_failed`.
   Compare as **sets** of `(path, after)`, so independent ops pass in any order; op shapes are never compared (`set_fields` ≡ `edit_list update slides[0]`, measured for both forms with and without `assets`, §2).
4. Verdict, first match:
   - `invalid_op` — any replayed op has `ok:false` (engine `E_*`), or the engine exited 1.
   - `unsupported_ok` — case kind `unsupported`, `report_unsupported` seen, zero ops.
   - `clarify_ok` — case kind `clarify`, zero ops, final text contains `?` and ≥ 2 candidate section names/ids.
   - `no_answer` — zero ops and the case expected ops (or `turn.error`, `stop ≠ end_turn`, no `turn.done`).
   - `wrong_value` — same path set, ≥ 1 `after` differs.
   - `missing_writes` — expected paths absent from actual.
   - `extra_writes` — actual paths not expected (checked after missing).
   - `pass` — identical sets.
   The row also stores `reasons[]` (all that apply), `info[]` (the non-failure notes: `companions`, `pick_substituted`, `pick_remeasure_failed`), `companions[]` (the set-aside leaves), `expected_diff`/`actual_diff` (mirror-aligned, companions still in them), `engine_errors`, `warnings`, and the engine identity (`engine_fingerprint` of the replaying engine, `case_engine_fingerprint` of the measuring one, `engine_mismatch`; §2). A clarify/unsupported case that produced ops is `extra_writes`.
   Tightenings beyond the list (verify.py, "never a vacuous pass of two empty sets"): a `clarify` case with zero ops whose reply does not clarify is `no_answer` (+ reason `not_clarifying`); an `unsupported` case with zero ops and no `report_unsupported` is `no_answer` (+ `not_reported`). A clarify that names one candidate, or has no `?`, is therefore `no_answer`, not `clarify_ok`.
   The replay's ctx is `verify.ctx_of(case)`: `templateId` (`site_state.template.id`, else `case.template`, else editorial) + golden ctx + the context's `locations` + `currentPage` = the case's `context.page` — the last added 2026-10-03 to match what `collect.ctx_for` sends live, because `headless.mjs` now fills a missing `target.page` from `currentPage` the way the browser host does (§2 "Fingerprint move of 2026-10-03"). The replay is of **every** `tool.call` in the trace, refused or not: a row collected under an older engine whose first op was refused and then retried is applied twice under the current one, so old runs are not re-scored across that fix.

Exact by construction: no figure extraction or grounding heuristics (thermometer's 3,696-line `verify.py` is replaced — FACTS 1 §8).

CLI: `souschef-lab verify --log <collect.jsonl> --cases <cases.jsonl> [--manifest M] [--out verdicts.jsonl]`. `M` is the manifest the cases were generated from (int-run1: `lab/data/int-run1/manifest.json`, canonical hash `907fc297…`); the default is `fixtures/manifest.snapshot.json` (`727d151b…`), a different manifest.

## 4. Collector (`collect.py`) — browser emulator

Replaces thermometer's synchronous `/api/chat` client (FACTS 1 §2, §8). Transport: Bearer `SOUS_CHEF_KEY`, `Accept: application/json` (events array, no heartbeats — FACTS 2 §3), `urllib` only. `run_case(case, route, k)`:
1. `POST /v1/manifests` once per process; assert returned `hash == case.manifest_hash`.
2. `DELETE /v1/conversations/lab-<case.id>` (`Client.end_conversation`; 204 whether or not one was open, a 404/501 from a fake without the route is tolerated), then `POST /v1/turns {siteId:'lab-<case.id>', storeId:'lab', manifestHash, buildId, context, text, model:route}`; `buildId` is `"lab"` unless `--build-id` says otherwise (the e2e run used `lab-e2e`). The DELETE is what makes every sample a **fresh conversation**: a turn without `conversationId` continues the site's open conversation (README §1.1), and the lab's `siteId` is the same for every sample of a case — measured 2026-10-01 against the real binary, the first model request of a re-collected case carried the previous run's four messages. The `lab-` site-id prefix is **reserved** (`usage.LabSitePrefix`, README §6): the service stores it as sent, but ships the usage rows of such a turn to the thermometer with no site and operation `lab_chat`/`lab_tool_turn`, so lab cases never show up there as sites. `run_case(…, fresh_conversation=False)` keeps the old behaviour; the row records `conversation_ended`. `context` is `render.turn_context(case)` (`case.context`, or `{}` — never null: the lab always sends an object and `prompt.ContextBlock` renders `{}` as `<context>\n{}\n</context>`); the row logs it as `context` and the text as `text`, and every rebuild reads them back (`render.turn_inputs`). The body goes on the wire as `render.compact_json(body)` — see "Prompt parity" below.
3. Per stream: collect `text.delta`; on `turn.waiting` run the batch's `tool.call`s (minus `report_unsupported`) through `engine.run` on the **running state** and `POST /tool-results {siteId, storeId, results:[{toolCallId, ok, error?, warnings?, written?, sectionId?}]}`; on `turn.suspended` answer `{toolCallId, ok:true, asset}` from `fixtures/assets.json` — `pick_asset_for` → `state.fixture_asset_for(assets, case_id, assetType, case.meta.asset_id)`: the asset is a function of the **case alone** — the asset the case names (`meta.asset_id`, when it is of the asked type), else `sha1(case id) % len(pool)` within the asked type — the same function the generator uses for the expected ops (§2), so the request text, the expectation and the pick agree and every sample of a case gets the same asset. Until 2026-10-04 (late) the name was ignored: a `url` request ("… the image 'Sunlit field at harvest'") made the model open the picker and the picker answered the hash pick — 15 of int-run3's 21 `url` rows failed on it (11 `wrong_value`, 4 `no_answer`; §2). Until 2026-10-04 it also hashed the service's random `toolCallId`, so no case could expect the right asset (int-run1's full run was collected with that picker — its pick rows verify through §3's substitution, which reads the picked asset from the row's `tool.result` events); loop to `turn.done`/`turn.error`. 409 `superseded` → drop, row `error:superseded`. Cap 8 batches (service `maxCalls`).
4. Record one row, fsynced on arrival (thermometer `append_row`), resumable on `status=="ok"`:

```
{id:"<case.id>#<k>", case_id, sample:k, model:route, status, http_status, code, error, latency_ms, context, text,
 messages:[…Anthropic blocks…], tools:[…], ops:[…], events:[…raw + tool.result…], verdict, reasons, written_paths,
 usage, stop, turn_id, conversation_id, conversation_ended, at, meta:{kind, section, template, field_type, holdout, manifest_hash, buildId, engine_fingerprint}}
```

`events` are the streams' events plus one `tool.result` event per posted item right after the stream it answers, exactly as the service's trace records them (`trace.go`: `data` = the item + `for_seq` of the `tool.call` — or of the `turn.suspended` for `pick_asset` — numbered on from the stream's last seq; the service's next stream continues after them, so the gap is real and the fake service leaves it too). With them `render.messages_from_events(row.events)` rebuilds `messages` exactly, and that rebuild — not the stored list — is what `dataset.to_hf` reads (§5 `messages_mismatch`).

`messages` is the turn as the model saw it: user = the context block; assistant = joined `text.delta` + one `tool_use{id,name,input}` per `tool.call` (+ the `pick_asset` tool_use rebuilt from `turn.suspended`, which carries the call — the service streams no `tool.call` for it; `render.pick_asset_call` rebuilds `{asset_type, purpose}` from the event's `assetType`/`purpose`: the tool schema is `strict` and requires both, so the model always sent both, and the captured history shows the input re-marshalled with sorted keys — the fixture `pick_asset.*` pins it); one user message of `tool_result` blocks per posted batch. Thinking is never available (traces don't store it) and never fabricated. `tools` = the ten README §2 tool **names** (the definitions come from `fixtures/prompt/tools.json` via `dataset --tools`; `to_hf` skips bare names). The row is a superset of thermometer's log row (FACTS 1 §2), so `to_hf` copies over.

**Prompt parity (`render.py`).** One renderer produces every byte the model reads that the lab writes itself, and it matches the service exactly (read-only references `service/internal/prompt/build.go` ContextBlock and `service/internal/loop/pending.go` browserResult):
- user block = `"<context>\n" + compact JSON + "\n</context>\n" + text.strip()`; a `null`/absent context gives the bare text. The service `json.Compact`s the RAW bytes the browser sent (key order kept, nothing re-encoded or HTML-escaped), so the collector serialises its request body with the same encoder and options (`render.compact_json`) that `render.context_block` uses — the bytes on the wire are the bytes in the log.
- browser `tool_result` = Go `json.Marshal` of a map: `{"hidden"?,"ok":true,"sectionId"?,"warnings"?,"written"?}` with keys **sorted** and empty lists omitted; `hidden` (2026-10-10, shared contract 4) is the browser's `[{key, by, byValue}]` next to `W_HIDDEN:<key>`, each entry a sorted map, entries without a string `key`/`by` dropped, a missing `byValue` `null` (`render.wire_hidden` = `loop/hidden.go` parseHidden); the collector posts it like the launcher (`client/turns.js` wireHidden: only on ok results, only when non-empty, never the engine's `rule`/`gate`) whenever the engine returns one; a failure = the flat `api.ToolError` struct `{"code","message","key"?}` with `is_error` (no `toolCallId`, nothing nested under `error`); a `pick_asset` answer = the `api.Asset` struct `{"public_url","alt"?,"srcset"?}` itself, or `{"code":"E_ASSET","message":"no asset was chosen"}` with `is_error`. Go's encoder is compact, keeps UTF-8, and escapes `<`, `>`, `&`, U+2028/9 as `<`… — `render.go_marshal` does the same.
- `collect.TurnRecorder` and `render.messages_from_events` share these functions; `dataset.context_block`/`messages_from_events` are aliases of render's. `dataset.to_hf` **always** rebuilds the turn from `row.events` (`dataset.rebuild_messages`: `render.turn_inputs(row, case)` for the context and text, then `messages_from_events`); a row's stored `messages` are a cache that must equal the rebuild or the row is rejected `messages_mismatch` (§5) — a log written before the renderer can no longer train silently on bytes the service never sent (the refuter found `to_hf` preferring the stale `row.messages` of the first real-binary capture).
- `tests/test_render.py` rebuilds every captured real-binary turn under `fixtures/prompt/real/<capture>/` (also `lab/data/e2e/real/<capture>/` when present) — the service's own `POST /v1/messages` bodies plus the collector row — and asserts, request after request, that the stored `messages`, the rebuild and the wire are the same text / tool_use / tool_result payloads, that every call carries the frozen prefix (`system0/1`, `tools.json`) byte for byte, and that `to_hf` reads those bytes. The four captures (`tests/capture_real.py`, recipe in `fixtures/prompt/real/README.md`) cover every shape `loop.browserResult` renders: ok/written, `E_FIELD` error with `is_error` then the retry, `sectionId` + `W_HIDDEN` warnings in one results message, and `pick_asset` → the bare `api.Asset` with `srcset`. Before this renderer the collector wrote `<context>{…}</context>\n` with no inner newlines and Python-spaced `{"ok": true, …}`, and `dataset` a third variant (`sort_keys`, spaces, `toolCallId` kept) — every HF row of the first e2e build carried bytes the service never sends.

Best-of-N: `--samples N` in rounds k=1..N with `bestofn.Adaptive` (`enough=2`; hopeless after ⌈N/2⌉ all-fail with family pass rate < 1/8 over ≥ 8 samples); `<log>-runs.jsonl` settings record; 1–4 workers via `run_batch`; `--max-cases` guard. Tests target only the fake service.

### Serving parity (`serving.py`, `parity/`, `fixtures/parity/served.json`; 2026-10-04)

**Rule: rows are rendered through the serving parity layer, never the base's chat template, and the parity fixture is re-captured when Ollama's renderer version changes.** `train.py`, `dpo.py` and `dataset --tokenizer` render a row with `serving.render_training` / `serving.render_prompt`, a Python replica of what Ollama 0.34.4 puts in front of the served student (the export's `RENDERER qwen3.5`, the service's `thinking: disabled`). The Hugging Face template r123 was rendered with wrote the same layout but not the same bytes — 0 of 10 tool definitions byte-identical, every echoed tool call different; ~729 of a row's ~11.6k tokens (6.3 %, LCS over token ids on 20 merged-r123 rows), from the first tool definition on — and a LoRA only shows a habit when served if it trained on the served tokens (the thermometer's K8 finding, `breadstack-thermometer/lab/in-house-model/lab/serving.py`, whose Go-format helpers are copied here).

What Ollama v0.34.4 does, and `serving.py` replicates (file:line at the tag):

1. **Tool definitions** — `anthropic/anthropic.go:665-681 convertTool` decodes `input_schema` into `api.ToolFunctionParameters` (`api/types.go:472-478`: `type`, `$defs`, `items`, `required`, `properties`) of `api.ToolProperty` (`api/types.go:417-425`: `anyOf`, `type`, `items`, `description`, `enum`, `properties`, `required`): keys without a field — `additionalProperties`, `minItems`, the top-level `strict` — are dropped, `required: []` and empty descriptions are `omitempty`, a one-member `type` is a string (`api/types.go:332-339`), `properties` keeps the schema's order (an ordered map, `api/types.go:353-415`) and is `null` when absent. The renderer writes the `api.Tool` with `marshalWithSpaces` (`model/renderers/qwen35.go:236-240`, `json.go:8-48`): Go `json.Marshal` — struct field order (`type, required, properties`; a property's `type, description, enum`), `<` `>` `&` as `<` `>` `&`, nested `any` values (`items`, `enum`, `$defs`) as maps with sorted keys — then a space after every `:` and `,` outside strings.
2. **Echoed tool calls** — the service re-sends each stored turn, whose `tool_use.input` Go re-marshalled from a map (top-level keys SORTED on the wire: `fixtures/prompt/real`, e.g. `edit_list` `action,item,list,target` where the model wrote `target,list,action,item`); `anthropic.go:485-503` keeps that order, and `qwen35.go:313-331` writes each parameter with `formatToolCallArgument` (`model/renderers/qwen3coder.go:200-222`): a string as it is, `nil` → `null`, a map or slice as COMPACT Go JSON (sorted keys, HTML-escaped), anything else with `fmt %v` (`1000000` → `1e+06`). `\n\n` between the turn's text and its first call, `\n` between calls.
3. **Thinking** — `{"thinking":{"type":"disabled"}}` → `think=false` (`anthropic.go:410-412`; `server/routes.go:2704-2706 ResolveThinking`): the qwen3.5 renderer writes NO think block on the assistant turns it echoes (`qwen35.go:299-311`, `isThinking && i > lastQueryIndex`) and ends the prompt with the EMPTY block `<|im_start|>assistant\n<think>\n\n</think>\n\n` (`qwen35.go:350-357`, `emitEmptyThinkOnNoThink`, `renderer.go:71-72`). The service drops stored thinking blocks from the history (`client.go dropThinking`).
4. **The rest** — system blocks concatenated with nothing between (`anthropic.go:335-348`), `TrimSpace` on every content (`qwen35.go:288`), tool-result text blocks concatenated (`anthropic.go:1043-1090`), one `<|im_start|>user` turn per run of `<tool_response>`s (`qwen35.go:336-343`), `<|im_end|>\n` after every closed turn. The Modelfile's `TEMPLATE {{ .Prompt }}` is never executed for chat (`server/prompt.go:135-143`); `filterThinkTags` touches only the `qwen3` family; `chatPrompt` truncates only over `num_ctx` (65,536; rows stop at 32,768).

The training text (`render_training`) opens EVERY assistant turn with the empty think block: each turn is the generation point of its own model call, so the span `train_on_responses_only` keeps (from `<|im_start|>assistant\n`) begins with the bytes the served prompt ends with, and the rest of the span is exactly what Ollama echoes of that turn in the next call (what its parser read back). The one residue a single sequence cannot avoid: Ollama renders call k's k−1 earlier assistant turns WITHOUT the block — 4 tokens per earlier turn, ~11k tokens back (84 tokens over the 40 calls of 20 r123 rows; `tests/test_serving.py` measures exactly that and nothing else). A DPO pair's prompt is the served prompt itself (`render_prompt`: no history blocks, the generation prompt), its completion the echo up to `<|im_end|>` — byte-exact. A row whose call Ollama would echo as another call (`serving.unservable`: an integer ≥ 1e6 → `1e+06`, a string starting or ending in a newline, the string `null`) is dropped and counted (`run.json` `rows.dropped_unservable`, the pairs' `unservable_call`; 0 in r123). `--thinking` is refused (the rows carry none; the service sends disabled).

**The fixture and its test.** `fixtures/parity/served.json` is Ollama's OWN render of every model request of the five real captures (`fixtures/prompt/real/*/model-requests.jsonl`: 12 requests — the fifth, `fields-context.*`, is the user turn with the candidate-fields block, below; every multi-call capture has `tool_use` + `tool_result`, one has two results in one turn, one a `pick_asset` suspension). `parity/` is a Go module of its own pinning `github.com/ollama/ollama v0.34.4` (the version `lab/model-image` serves) that runs the server's path on each captured body with no model loaded — `anthropic.FromMessagesRequest` with the qwen3.5 thinking descriptor, `renderers.ResolveThinking`, the qwen3.5 parser's `Init`, `RenderWithRenderer("qwen3.5")` — the chain the 2026-10-04 parity review ran offline to find the skew; it builds from the Go module cache without network (`GOTOOLCHAIN=auto` picks go 1.26, the version the module needs). `make -C lab parity-write` records the fixture, `make -C lab parity` re-renders and diffs. `tests/test_serving.py` holds `render_prompt` to the fixture byte for byte for all 12 requests, checks the training text is those bytes up to each generation point minus the residue, that every trained span is the empty think block + Ollama's echo of that turn, that the DPO render is the served prompt + echo, and re-runs the harness when `go` is on PATH (`SOUS_CHEF_LAB_REQUIRE_GO=1` makes a missing Go a failure). **Re-capture when Ollama's renderer version changes** — a bump of Ollama in `lab/model-image`, of `RENDERER`/`PARSER` in the export's Modelfile, or of how the service builds a request (`client.go`): bump `parity/go.mod`, `make -C lab parity-write`, fix `serving.py` until `make -C lab test` is green, then rebuild the dataset (`over_length` counts tokens on this render) before training.

Pick: `rank_key` adapted — pass first, fewest browser ops, fewest server-tool calls, shortest reply, sample number. `select` copied: p90 length guard per kind, `max_seq`, one row per case plus a second when its op path is not a superset, family cap 0.03 (family = section type / panel).

DPO pairs (`pairs.py` copied): chosen = pass, rejected = `extra_writes|wrong_value|missing_writes|invalid_op` of the same case (`no_answer` is INCOMPLETE, never rejected). `split_point`: `final` (same ops and results, different text) or `divergence` (first assistant turn whose ops differ; prompt = shared prefix). Rejected used once, ≤ 2 pairs per prompt, ≤ 36,864 tokens per side, ≥ 50 % chosen-no-longer-than-rejected. Row `{id, prompt, chosen, rejected, tools, meta}`.

Splits: `train.jsonl`/`val.jsonl` by `sha1(case_id) % 100 < val_pct(10)`, `exam.jsonl` = holdout cases, `rejects.jsonl`, `stats.json` (rejects by first and by any reason, verdict histogram by kind, `engine:{fingerprint, case_fingerprints, stale_cases}`), `dataset-manifest.json` (log files, manifest hashes, `engine_fingerprint` of the build's engine and `case_engine_fingerprints`, rule version, counts). HF `meta.engine_fingerprint` is the case's. A build whose cases were measured by another engine prints a warning naming `cases remeasure`.

### Candidate fields (`fields.py`, `service/cmd/sous-chef-fields`; 2026-10-04)

**Rule: a row trained for the served student carries the `<candidate_fields>` block the service sends, computed by the service's own code — never a Python port.** The student's route (`messages-compatible`, `fields_context` on by default — service README §5) gets, between `</context>\n` and the merchant's text, a block listing the op target(s) and field keys the request most likely means (`service/internal/fields`; `prompt.UserText`). The exam showed why: 110 of the r2 student's 142 failures were an invented key on the right target. The Anthropic routes send no block and are byte-identical to before.

- **One implementation.** `fields.py` builds `service/cmd/sous-chef-fields` once per process into `lab/.cache/fields/` (`go build`; `SOUS_CHEF_FIELDS_BIN=<binary>` skips the build) and shells out with `-jsonl` — one process for a whole build (1,000 turns ≈ 3 s). `fields.Fields(manifest).block(context, text)` is the block for a turn (text trimmed first, as the service does; `""` when nothing matches or the retrieval cannot read the context — the service then runs the turn without one). `render.context_block(context, text, candidates)` places it where `prompt.UserText` does.
- **Dataset option, default on.** `souschef-lab build --fields-context on|off|as-logged` (`make dataset FIELDS_CONTEXT=…`). `on` renders EVERY kept row's user turn with the block computed now for that row's context and text — the Claude teacher rows were sent none and get one; it needs `go` and the cases' manifest (`--manifest`, default `manifest.json` beside `--cases`, else the fixture snapshot; refused when its hash is not the cases'). `off` renders none. `as-logged` keeps whatever each row was collected with (the library default of `BuildConfig`/`Judge`/`to_hf`; `pairs` uses it, since DPO pairs are the student's own samples). Recorded: `meta.fields_context` / `meta.fields_block_chars` per row; `dataset-manifest.json` `fields_context {enabled, mode, cli, source_sha256, manifest_file, manifest_file_sha256, rows, rows_with_block}` (`source_sha256` = sha256 over the non-test Go sources of `internal/fields` and the CLI — a retrieval change is a new value, and the Go goldens `internal/fields/testdata/*.golden` are the tripwire that says the rows must be re-rendered); `stats.json` adds the block's size and `drift` (rows logged with another block than the one rendered).
- **Train option, default on.** Training never renders the block (the training VM has no Go): `train --fields-context on|off` (`make train FIELDS_CONTEXT=…`) CHECKS the rows — `on` refuses a set where no user turn carries a block, `off` one where any does — and `run.json` records `fields_context {enabled, rows, rows_with_block, dataset: <the dataset manifest's entry>}`. That is how an adapter trained with the block is told from one trained without; serve the former on a route with `fields_context` on and the latter with it `off`.
- **Re-rendering a built set.** `souschef-lab fields rerender --data <set>/dataset --manifest <set>/manifest.json --out <new set>/dataset` (`make fields-rerender DATA=data/<set> OUT=data/<new set>`) rewrites only the first user turn of `train.jsonl` / `val.jsonl` (the `<context>` line is kept as bytes, the block inserted or — `--fields-context off` — removed; the `--manifest` must hash to the rows' `meta.manifest_hash` and the dataset manifest's `manifest_hashes`, else it exits 1 and writes nothing), copies the other files and writes `dataset-manifest.json` with `fields_context` and `rerendered_from`. It never writes in place. For the r123 set: `make -C lab fields-rerender DATA=data/merged-r123 OUT=data/merged-r123-fc` (2.6 s; measured into a scratch folder 2026-10-04: 604 of 605 rows gain a block, chars p50 979 / p95 1,894 / max 4,078 on train; the dry-run estimate goes from ≈15.5k to a median of 15,885 tokens, max 16,976, none over 32,768), then `make -C lab train DRY=1 DATA=data/merged-r123-fc`.
  **System turn too (2026-10-10).** `--system index` also replaces system[1] with the index the service renders now (`service/cmd/sous-chef-prefix`, `fields.Prefix`; the row's system turn is split at the index header `# Manifest index`), keeping the rules the row was collected under; `--system prefix` replaces system[0] + system[1] + the tools (`dataset.hf_tools` of the wire tools). Both are checked against the rows' manifest like the block, recorded per row (`meta.system_rerendered`) and in `dataset-manifest.json` (`system_prompt`: the prefix CLI's source sha, system0/system1/tools sha256, rows changed). `fields.source_sha` now also hashes the embedded `internal/fields/vocab.txt` (before, a vocabulary-only change left the recorded identity unchanged). Built 2026-10-10 from `data/merged-r123-fc` (3.3 s each): **`data/merged-r123-fc-v2`** (`--system index`) — 605 rows (train 543 / val 62), 605 with a block (was 604), **173 blocks changed** (train 143, val 30; chars p50 954 / p95 1,794 / max 3,832 on train), system[1] changed on all 605 (11,546 → 12,827 chars on the snapshot: the vocabulary's `also called` lines), rules and tools as collected; dry-run tokens median 15,885 → 16,302, max 17,296. **`data/merged-r123-fc-v2-prefix`** (`--system prefix`) — the same plus the 2026-10-10 rules and tools on all 605 rows; median 17,805, max 18,823. **Re-rendered the same day after the verify pass** (both directories rebuilt from `data/merged-r123-fc`, the earlier builds kept outside the repo): the rules, tools and index wording changed again (README §3; the index's gallery line gains "instagram feed"), and the vocabulary's narrower "add a …" and gallery aliases moved 2 train blocks (an "add a FAQ category" row's; "Put an Instagram feed widget under the gallery" — not something the editor can do — now gets none: 604 rows with a block, train 141 / val 30 changed against `merged-r123-fc`). **Do not train the prefix set as is:** 533 of its 605 rows (train 477, val 56) end with a reply that mentions the preview, 498 of them "the live preview" (the teacher followed the old rules), which the new rules forbid (contract 3: never claim a change shows in the preview); and 7 rows (train 6, val 1) call `report_unsupported` without `where`, which the new rules always set — re-collect, or rewrite those replies and calls, before a retrain on the new rules.
- **Collect / eval follow the service (`--fields-context auto`, the default).** The collector cannot see the prompt, so the service says: `GET /version` states each route's `{kind, fields_context, fallback, report_as}` beside the `routes` name list (`route_info`, keyed by route name, plus `default_route`; a list of `{name, …}` entries is read too), and `turn.done` carries the turn's (`route: {name, fields_context, fallback, model}`; a top-level `fields_context` is read too). `collect|eval` read the route's entry at start (`make collect|eval`, `ROUTE_FIELDS_CONTEXT=auto`); when it is on they compute the same block (needs `go`) and log it as `row.candidate_fields` (`""` when nothing matched), `row.messages` carry it, and `render.messages_from_events(events, context, text, candidates)` rebuilds them. `on` / `off` say it by hand and are **refused when `/version` says otherwise**; they are only needed against a service built before the statement, where `auto` refuses to guess. Every `turn.done` is checked again: one that contradicts what the collector rendered stops the run before the row is logged (`collect.FieldsContextMismatch`). Recorded: `row.fields_context` + `row.fields_context_by` (`service` when turn.done said so, `flag` otherwise), and `fields_context_by` / `route_info` in the runs record and the eval report. The option changes nothing the service does or the verdict — only whether the logged messages are the bytes the model read.
- **Pairs and DPO check the rows.** `pairs --fields-context as-logged` (the default) refuses a log whose samples were collected partly with the block and partly without, and `pairs-manifest.json` / `stats.json` record `fields_context {mode, enabled, pairs, pairs_with_block}`. `dpo --fields-context auto|on|off` (`make dpo DPO_FIELDS_CONTEXT=…`) checks the pairs as `train` checks its rows — `auto` (default) = what the SFT adapter it continues was trained with (`run.json` `fields_context.enabled`; an adapter from before the block = off); pairs with no block are refused when it is on, pairs with one when it is off, and a flag that contradicts the SFT run is refused — and `run.json` records `fields_context {enabled, by, sft_enabled, pairs, pairs_with_block, pairs_manifest}`.
- **Parity.** `fixtures/prompt/real/fields-context.set_field.contentBlock-1.title` is the real binary on a second fake route (`lab-fake-fields`, `fields_context: on`; the four older captures' route now says `off` explicitly): `tests/test_render.py` holds stored == rebuilt == wire for it like every capture, `tests/test_fields.py` adds that the lab's CLI block is the captured one, that the block-less capture's built row re-rendered with `fields rerender` equals the wire byte for byte (and back), and that system and tools are identical on both routes; `tests/test_serving.py` holds the served render of the turn to Ollama's own. The Go-needing tests skip without `go` (`SOUS_CHEF_LAB_REQUIRE_GO=1` fails instead), as the serving-parity re-run does.

## 6. Eval and pass@k

`eval.py --route R --label L [--samples n]` runs every exam case through `collect.run_case` + `verify`, writes `runs/eval-<L>-<UTC>.json`: pass rate overall / by kind / by section or panel / by field type, verdict histogram, ops per turn, p50/p95 latency, usage. `--compare A B` = per-case agreement and flips; `--rescore` re-verifies under current rules.

`passk.py` (copied): pass@k = 1 − C(n−c,k)/C(n,k), k ∈ {1,2,4,8}, over runs sharing route, manifest hash and rule version; by kind; learnable band (1…n−1 of n); headroom = pass@4 − pass@1, ≥ 5 points → "SFT then DPO", else "stop".

**Thinking at serve (headroom / base eval, 2026-10-04).** The service's `messages-compatible` routes now default to `"thinking":"disabled"` (service README §5): the body carries `{"thinking":{"type":"disabled"}}`, which Ollama 0.34.4 maps to `think=false`, so the qwen3.5 renderer emits the **empty** `<think>\n\n</think>` block — byte-identical to every SFT row's assistant span (`train.py` writes the empty think block first) — and stored thinking blocks are dropped from the re-sent history. Before this the field was stripped, Ollama's default `think=nil` rendered an **open** `<think>`, and the base rows in `runs/` were measured with thinking ON (half the output tokens untraced thinking, 5/229 `max_tokens` with 0 calls). Consequence for the headroom decision: **the base eval must be re-run on the same routes before an adapter is compared against it** — `lab/headroom.env` already carries the default; the earlier base numbers are not comparable. To measure the thinking-on variant deliberately, add `"thinking":"enabled"` to that route (and label the run so `passk` does not pool the two).

**Hybrid (a route with `fallback`; service README §4; 2026-10-04).** On a route with a `fallback` the service hands the turn to the fallback route at most once — the student's op was refused (`tool_error`), it reported `unsupported`, its call failed (`model_error`) or stopped at `max_tokens`, or (2026-10-10, plan Q9) an applied op wrote a field that comes back `W_HIDDEN` with its gate closed (`hidden_write`: judged from the result's `hidden` member against the manifest rule; without the member — the frozen engine snapshot, the launcher deployed before contract 4 — no hand-off, since the engine warns on open gates too) — and emits `turn.escalated {from,to,reason}`; `turn.done` then lists `routes` and `models` (route → the model id its calls were reported under). **No route name is special**: the lab reads names from `--route`, `/version` and `turn.done`. The in-house model's route on int is `blueberry-muffin` (it also sets `report_as: "blueberry-muffin"`, so the service's usage rows and `turn.done` name it that way instead of the Ollama tag — service README §5); `lab/headroom.env`'s examples use the same name.

- **Recorded per row** (`collect.run_case`, so `collect` and `eval` alike): `escalated` (`{from,to,reason}` or `null`) and `routes` (turn.done's list; `null` on a route without a fallback). `row.model` stays the route that was ASKED; `row.models` (when turn.done states it: `route.model`, and `models` on a hybrid turn) is route → reported model id, e.g. `{"blueberry-muffin":"blueberry-muffin","default":"claude-sonnet-5-5"}`.
- **Three figures** (`collect.hybrid_summary`; `eval`'s `summary.hybrid` and a `hybrid` line in the printed summary, `collect`'s last line over the whole log — both only when a fallback was seen; `summary.hybrid.student` = `{route, model}` is who the student was — the route asked and the model id the service reported for it — and the printed line is labelled with it, `blueberry-muffin-only pass …`, falling back to the route name, then to `student`): **student-only pass** = rows that never escalated and passed, over all scored rows (and over the rows the student kept, `pass_rate_unescalated`); **hybrid pass** = those plus the escalated rows the fallback finished correctly; **escalation rate** = escalated rows over all rows, with the reasons. `summary.overall` is unchanged — the verifier's verdict as is.
- **Why the hybrid pass is not the verifier's verdict.** `verify` is strict about the path: one refused op makes a row `invalid_op` even when the turn then lands the expected diff (a refused op applies nothing). On an escalated turn the student's refused op is exactly what the fallback is there to correct, so `collect.outcome_passed` forgives it: an escalated row passes when `invalid_op` is its ONLY failing reason and every refused result precedes the `turn.escalated` event. A refusal of the fallback's own op stays a failure, as on a Claude-only route, so the figure is comparable to Claude's strict exam score. `hybrid.strict_pass_rate` is the unforgiving number; `RULE_VERSION` did not move (no verdict changed).
- **Escalated rows in the dataset.** A row whose turn escalated was finished by the fallback's model. `build` keeps it only under the usual keep rules — so a `tool_error` escalation is rejected `not_pass` (its verdict is `invalid_op`), and what survives is a turn the fallback answered whole (`unsupported`, `model_error`, `max_tokens`) or finished after the student's applied write (`hidden_write` — the student's op is in it, so the row is the teacher's like any other escalated row) — and flags it: `meta.escalated`, `meta.escalation_reason`, `meta.requested_model` = the student route, `meta.model` = the route that finished it. It is a teacher row, never the student's; `stats.escalated` / `dataset-manifest.json` `escalated_rows` count them and `--drop-escalated` rejects them (`escalated`). `pairs` excludes escalated samples outright (`escalated_excluded`): neither a chosen nor a rejected answer of the student.
- **Running it.** `lab/headroom.env` has the commented hybrid `MODEL_ROUTES` (student route + `fallback`, the fallback an Anthropic route — that one spends API money and needs `ANTHROPIC_API_KEY`). `souschef-lab eval --route <student> …` (`--fields-context auto` reads the route's `fields_context` from `/version`).

## 6b. The real-phrasing exam (`exam.py`, `fixtures/exam/`; 2026-10-10)

**Why.** The generated exam (§2) quotes the editor's labels word for word, runs a median of 12 words, is single-turn and uses one template, so the candidate-fields block finds the right key on 100% of it — while on the user's real turns of 2026-10-06 (two `vintage` sites, all answered first by blueberry-muffin) the right setting was missing from the block in 13 of 16 readable turns. This exam measures the gap: everyday phrasings, follow-ups with history, requests the editor cannot do, and a replay of real conversations. **Every phrasing was written by the 2026-10-10 paraphrase study, not by merchants**, except the `real` set (the user's own turns, with a key the study judged correct).

**Sets** (`fixtures/exam/<set>.jsonl`, listed by `make -C lab exam-sets`; `sets.json` records sizes, sources by sha256 and the manifest):

| set | rows | what |
|---|---|---|
| `paraphrase` | 147 | in scope; classes synonym 74, unnamed 29 (no section named, the viewed page carries it), relative 14, followup 12, compound 10, selected 8 |
| `holdout` | 62 | written after the study froze its prototype's tables (synonym 40, relative 10, unnamed 6, followup 4, selected 2) — the honest estimate for any retrieval change tuned on `paraphrase` |
| `real` | 14 | the user's real turns with a known right key (12 with the turn before as history) |
| `out_of_scope` | 13 | products, prices, new pages, template switch, domain, discount codes, deleting a category, email, live chat, translation, site URL, bitcoin, sales figures |
| `out_of_scope_holdout` | 4 | written with the holdout (a new location, removing products, loyalty, Google Maps hours) |
| `followup` | 12 | the paraphrase rows of class followup ("6", "yes please", "okay, lora", "max" …), each with `history` = the previous user text + assistant reply |

**Row** = the case schema (§2) minus the measured diff: `{id, set, kind: phrasing|out_of_scope, target, fields, site_state: null, context_ref, request, history: [{user, assistant, context_ref?}], expected: {ops: [], diff: [], keys: [{target, key, list}], alt: [[…]], out_of_scope: null|{reason, where, expected_where}}, holdout: true, manifest_hash, engine_fingerprint: null, template: "vintage", meta: {class, page, source, context_source, selected_section_id?, recorded_turn?}}`. `expected.keys` is what the request means (`list` = a list's name, `key: ""` = the list itself); `alt` holds whole alternative sets (the SEO panel's `defaults.title` for "site name", `headingFont` beside `bodyFont`). **Values are not scored** — "make it rounder" has no one right number. **The manifest is recorded by hash**: `fixtures/exam/manifest-real.json` is the real manifest of build 9cc1cd1 (hash `bf788701…`, the one the real turns ran on), every row carries that `manifest_hash`, `sets.json` adds the file's sha256, and `exam.load_set(…, manifest=…)` refuses another manifest. **Contexts** (`contexts.json`, inflated by `load_set`): the recorded browser context of the user's turns for home, products, product-details and faq (`context_source: recorded`; the real turns' own contexts for `real`); for the other pinned pages an approximation (the home context's lists, `layout: "default"`, `sections: []` — the browser never lists a pinned section; `context_source: approximated`). They are the 10-06 browser's contexts: no `selectedSectionId` (kept in `meta.selected_section_id`; `--with-selected` adds it) and none of the members the context work of 2026-10-10 adds (`focus`, `shopMenu`, `outline`) — re-derive the contexts when that ships, or the exam keeps measuring the old browser. Every expected key is checked against the manifest at build (`exam.check_expectation`, with the engine's own resolutions: page `seo` = `details.SeoPanel`, a page's `sections` list, `categories.<slug>.<field>` = the global `categories` map + `CategoryDetailsPanel`) and, authoritatively, by the oracle dry run below.

**Offline retrieval score (no model).** `make -C lab exam-retrieval SET=<set|all>` runs every row's context + text through the service's own retrieval (`internal/fields` via `cmd/sous-chef-fields`, built by `fields.py`; `--bin` takes a prebuilt one) and scores **recall@block**: the block lists every key of the expected set (or of one alt set) under the right target. Also reported: target missed (the right section/panel is not in the block at all) vs key missed, `top1` (the first target already holds the answer), empty blocks, block chars p50/p95, and for out-of-scope rows how many still get a non-empty block (an invitation to write something). `WITH_HISTORY=1` is a what-if that always reads the previous user text + reply with the request; `FOLLOWUPS=1` (`--follow-ups`) instead hands each row's `history` to the service's own rule (`fields.CandidatesAfter`: only a reply of at most three content words that names nothing is read with the turn before it — what the loop serves once it passes the previous turn, README §3); `WITH_SELECTED=1` sends the selected section as the browser does since the 2026-10-10 context work, `focus: {area: "editor", sectionId, panel: ""}` (and the older `selectedSectionId`). The scorer is the study's (`harness.py`) rule: on the study's own contexts it reproduces its 147/62/14 numbers exactly; with the recorded contexts two product-details rows (p084, p085) flip to a miss, because the real context lists no pinned section.

**End-to-end score.** `make -C lab exam-run SET=<set> ROUTE=<route> LABEL=…` (SPENDS model calls on whatever `SOUS_CHEF_URL` names) sends each row through `collect.run_case` — the browser emulator, the real engine on a `vintage` EditorState built from the home context's sections (`exam.vintage_state`) — and scores the ops **the engine accepted**: `pass` = every key of the expected set (or one alt set) written and nothing outside expect ∪ alt (a nested value counts once, by its top-level key); `stray_writes` = all written plus something else (the HashiTong turn's "Show Location Name"); `partial`; `wrong_target`; `no_write` (asked or answered instead — a sensible question still fails here); `invalid_op` (only refused ops). Targets match like the engine fills them (a section target without `page` is the viewed page; a global target without `panel` is the merged settings; a list row's key also matches the hero's flat `slides[0]` mirror). **Out of scope** passes as `unsupported_ok` (so `collect.passed` and `eval`'s figures count it unchanged) when the turn made **no accepted write** and its words — the reply, or `report_unsupported`'s `reason` / `manual_hint` — **name a place to go**: one of `exam.PLACE_TERMS` (Breadstack, CRM, dashboard, admin, POS, store settings, support, catalog manager, registrar, DNS, Google Business …, whole words) or one of the row's own `where` words; otherwise `wrote` or `no_pointer`. Deliberately a keyword rule — Q3's "where each one lives" list should replace the terms once it exists. The run lands in `runs/exam-<set>-<label>-<UTC>.json` (`eval.build_report`'s shape plus `summary.by_class`, `summary.keys_hit` = expected keys written regardless of strays, `summary.escalated`, `history_mode`), so `eval --compare` works on two runs. **Multi-turn rows** replay their `history` first: each earlier user text is a live turn of the same conversation (one `DELETE` before the first; the engine state carries over), then the scored turn; `HISTORY=live` (default, every history turn), `last`, `none`. The service cannot seed a recorded assistant reply (`POST /v1/turns` takes no history and there is no seed endpoint), so the replayed turns re-ask the model — each row records `history_turns[]` with the live reply beside the recorded one, and a follow-up whose live predecessor answered differently ("Want me to make the buttons pink too?" never asked) measures something else. A seed endpoint (`PUT /v1/conversations/{siteId}` with messages, lab keys only) would make the replay exact — a service change, not made here (§13). What the scored turn's request holds of that history is the service's (README §3 "Stable history", 2026-10-10): on a `messages-compatible` route the earlier turns go out as their request text, tool calls and replies (no `<context>`/`<candidate_fields>` blocks); on an `anthropic` route as stored; and a follow-up's candidate-fields block is read with the previous request and reply (`fields.CandidatesAfter`, what `exam-retrieval FOLLOWUPS=1` measures offline).

**Out-of-scope scoring with `where` (2026-10-10, shared contract 1).** Every out-of-scope row carries `expected_where`: the `report_unsupported.where` values that pass it (`exam.WHERE_VALUES` = the service's `toolgen.UnsupportedWhere` = the launcher's `deepLinks.js WHERE`), derived at build time from reason + request (`exam.expected_where_for`: template → themes, domain/slug/site URL → domain, new page → pages, category → categories, product/price/catalog → products; payments, discounts, loyalty, messaging, locations, analytics and Google listings → support). The 17 rows: products p135 p136 h064, pages p137, themes p138, domain p139 p145, categories p141, support the other 9. `score_turn`: any accepted write → `wrote`; else when a `report_unsupported` call carries a `where` the browser can link (trimmed, lower-cased, an enum member) the row passes iff it is one of `expected_where` (`unsupported_ok`, else **`wrong_where`**, a fail), `scored_by: "where"`; with no usable `where` (a baseline before the enum, or a value outside it) today's keyword rule scores the reply, `scored_by: "keywords"` — so a baseline revision is scored as before. Rows record `where_sent`, `expected_where`, `where_raw` (when the model sent something the browser ignores) and `reported`, and **`keyword_verdict`**: the keyword rule on the reply's words for every row whatever `where` says (`wrote` / `unsupported_ok` / `no_pointer`) — the primary verdict measures a candidate that sends `where` and a baseline that cannot differently (a baseline's "contact Breadstack support" passes p139, a candidate's `where:support` there is `wrong_where`), so the keyword verdict is the symmetric secondary score.

**Row ranges and separate conversations.** `exam run --offset N --limit M` (`make exam-run|exam-dry OFFSET=… LIMIT=…`) runs rows N..N+M-1 of the set (after `--only`); the report records `rows_range {offset, end, of}` and the file name gains `-r<from>-<to>`, so parallel chunks of one set never overwrite each other. `--site-prefix lab-cand-` (`SITE_PREFIX=`, must start with `lab-`; default `lab-`) makes the siteId `<prefix><row id>`, so a baseline and a candidate revision on one database keep separate conversations (`collect.run_case(site_prefix=)`).

**Comparing runs.** `python -m souschef_lab.examcmp --run base='runs/…/exam-*-base-*.json' --run cand='…'` merges each revision's chunks (by row id; a later report wins a row; a missing chunk shows as `(of N!)`) and prints pass rate per set × route × revision — transport errors count as fails, `scored` beside it — with Wilson 95 % intervals, the verdict breakdown, escalations, p50 latency and cost from the rows' usage (Sonnet 5.5 $2/$10/$2.50/$0.20 per MTok for input/output/5-min cache write/cache read, Opus 5.5 $4/$20/$5/$0.20; a hybrid route's escalated rows priced whole at the fallback's model, flagged `≤`; `--gpu-hourly` × wall-clock for the GPU route), escalations by reason (with pass rate and cost without the `hidden_write` hand-offs when there are any), the out-of-scope `kw` count (`keyword_verdict`, both revisions alike), and a **paired** table: per set × route and pooled per route, the rows both revisions ran split into both pass / first only / second only / neither, with the exact two-sided McNemar p on the discordant rows — same rows on both sides, so it sees differences two independent Wilson intervals (±12 points at n = 62) cannot. `--json` writes `{groups, paired}`. A run report never overwrites another: a second report of the same set, label and range in the same second gets `-2`, `-3` … (`exam.unused_path`). ## 12. Engine gaps found by the lab (for the cookie-cutter engine workflow — not fixed here)

Found while measuring cases and probing the verifier against `launcher/client/src/sousChef/ops` (cookie-cutter `sous-chef-v2`, 2026-10-01). Each is reproducible through `headless.mjs`; none is worked around in the lab.

1. **`orders` lists accept arbitrary ids.** An `edit_list reorder` on an `orders` list (e.g. `paymentMethodsOrder`, README rule 7: "reorder by id array") validates only the entry *types* (`validate.js:273-276`), and `transforms.reorderByIds` (`transforms.js:640-650`) writes whatever it was given verbatim: `["visa","mastercard","bogus"]` lands `bogus` in state, and `[1,0,2]` (integer indexes, the shape of ordinary lists) is written as the new order too. Expected: unknown ids → `E_INDEX`/`E_ENUM`-class refusal; integers refused on an `orders` list; probably also "every known id exactly once". The verifier catches these only as `missing_writes`/`extra_writes` rather than `invalid_op`, so a model that learns bogus ids is not told why.
2. **Keyed `locationOverrides.<id>.*` targets other than `address` are `E_FIELD`** (31 writable targets skipped at generation, `skip:keyed-not-resolvable`): the manifest lists them as keyed_by fields but `targets.js` resolves only `address`. Same family: `footerLocationOverrides.<id>.*`.
3. **`headless.mjs` truncates a piped stdout at 64 KiB** (`process.exit` right after `process.stdout.write`; a 300 KB `--print-state` reply arrived as 65,511 bytes through Python's pipe, 131,072 through a shell pipe on Node v23.5.0). The lab reads `--out <file>`; awaiting the write (or setting `process.exitCode` and returning) would let the pipe be used again.
4. **`W_HIDDEN` is emitted for every gated field whether the gate is open or closed** (`validate.js` `isGated`), so the warning cannot distinguish "wrote a hidden field" from "wrote a field that has a gate" — the lab's `warnings` keep rule has to subtract the case's own measured warnings (§5). A warning only when the gate is actually closed in the state would make it meaningful.
5. **Engine behaviour moved under measured cases** (2026-10-01 21:52–21:53: `engine.js`, `validate.js`, `schema.js`, `targets.js`): `reset` of a `writes` partner now also clears the partner (`tagSlug` → `tagId: null`, `brandSlug` → `brandId: null`, `mapLocationIndex` → `mapLocationId: null`) and `restore_default` applies the preset's writes (`storeMode` → `footerLayout: "classic"`, `showLocationInHeader`). Not a bug — but it is why cases carry an `engine_fingerprint` (§2); an engine CHANGELOG line per behaviour change would let `cases remeasure` be scheduled instead of discovered.
6. **FIXED 2026-10-03 — `headless.mjs` did not fill `target.page` from `ctx.currentPage`.** The browser host runs every batch through `previewApi.withTargetDefaults(ops, ctx)` before `applyOps`; the headless runner called `applyOps` directly, so an op the tool description explicitly allows (section target without `page`, "the host fills it in") was `E_TARGET "section target needs a page"` in the lab only — 16 `invalid_op` rows in int-run2, all `context.page = 'home'`, each an error + a retry with `page`. Fixed in cookie-cutter `headless.mjs` (lab-facing only; nothing changes in the browser path), tested in `ops/headless.test.js` and `tests/test_engine.py`; the engine fingerprint moved (§2). Lab side of the same gap: `verify.ctx_of` did not send `currentPage` either (only `collect.ctx_for` did) — fixed with it, or the replay would have refused what the collector accepted.

## 13. Service doc gaps (for the service workflow — `README.md` is read-only here)

1. `turn.done` carries `conversationId` (`loop/turn.go:467`; the collector records it as `conversation_id`), and `conversationRotated:true` on rotation; the README §1.2 event table lists only `usage` and `stop` for `turn.done`.
2. The README does not say that `pick_asset` has **no** `tool.call` event — `turn.suspended` carries the call (`toolCallId`, `purpose`, `assetType`, and `toolCallIds` when other ops share the batch). A trace reader rebuilding the assistant turn must synthesise the `pick_asset` tool_use from it (`render.pick_asset_call`); the event drops the model's `input` object, so the rebuild leans on the tool schema (`strict`, both keys required) — carrying `input` verbatim (as `tool.call` does) would make the rebuild schema-independent.
3. The rendered per-turn bytes (`prompt.ContextBlock`: `<context>\n…\n</context>\n`; `loop.browserResult`: Go-marshalled map with sorted keys, flat `{code,message,key}` errors, the bare `api.Asset` for `pick_asset`) are documented only in code; README §3 says "the `<context>` JSON, then the merchant text". A one-line byte spec would let any trainer check parity without reading Go.
4. No way to seed a conversation with recorded turns (§6b): `POST /v1/turns` takes no history, so the exam replays a follow-up's history by re-asking the model each earlier turn, and the replayed reply can differ from the one the merchant answered. A lab-only seed (e.g. `PUT /v1/conversations/{siteId}` with `{messages}` under a lab service key, rejected for launcher keys) would make multi-turn exam rows and the conversation replay exact and cheaper (one model turn per row instead of n+1).
